# Tessera v1.1.0

**Release date:** 2026-06-11

## Summary

This release introduces a registry-based architecture for layout and routing
algorithms, three new algorithms (SABRE layout, A\* routing, SABRE routing),
and a multi-pass optimization loop. The `transpile()` public API gains
`layout_algorithm`, `optimization_iterations`, and `max_iterations` parameters,
all backwards-compatible at their defaults so existing code keeps working
unchanged.

---

## New Features

### Multi-Pass Optimization Loop
A new `OptimizationLoopPass` wraps a list of optimization passes and runs
them either a fixed number of iterations or until gate count converges.
Pluggable into the main pipeline; default behavior (single iteration) is
identical to the previous one-pass design.

- `optimization_iterations` parameter on `transpile()` and `TesseraTranspiler`
  - `1` (default): single pass — preserves existing behavior
  - positive `int`: run the inner passes that many times
  - `-1`: run until gate count stabilizes (convergence mode)
- `max_iterations` parameter (default `1000`) caps convergence-mode runs
- `debug_on=True` logs per-pass gate counts inside the loop
- Pipeline integration: wraps `CancelAdjacentPass + MergeRotationsPass`

### Layout Registry Architecture (`LAYOUT_REGISTRY`)
Layout selection is now a registry lookup. The new `LayoutPass` resolves a
layout algorithm name (string) or custom callable at construction time.

| Algorithm | Description |
|-----------|-------------|
| `"dense"` (default) | Greedy interaction-frequency placement (migrated from `DenseLayoutPass`) |
| `"sabre"` | Forward-backward trial routing for initial mapping discovery |
| `"trivial"` | Direct logical→physical mapping (migrated from `TrivialPass`) |

- New module: `tessera/layouts/` containing the algorithms and registry
- New parameter: `layout_algorithm` on `transpile()` and `TesseraTranspiler`
- Custom callables accepted: `(circuit, coupling_map) -> dict[int, int]`

### Routing Registry Architecture (`ROUTING_REGISTRY`)
Routing strategy selection is now a registry lookup. `BasicSwapRouter`
resolves a routing strategy name (string) or pairwise callable at
construction time.

| Algorithm | Description |
|-----------|-------------|
| `"bfs"` (default) | Breadth-first pairwise pathfinding (migrated from inline class method) |
| `"a_star"` | A\* pairwise pathfinding with hop-distance heuristic |
| `"sabre"` | Whole-circuit heuristic swap selection with front-layer lookahead |

- New module: `tessera/routing/` containing the algorithms, registry, and shared `pairwise_route` engine
- **Routing algorithm selection uses the existing `pathfinder` parameter** on `BasicSwapRouter` and `transpile()` — name kept intentionally for backwards compatibility with v1.0.x callers who were already passing custom callables. The parameter is asymmetric with the new `layout_algorithm` parameter by design.
- `pathfinder` now accepts:
  - a registered algorithm name (string): `"bfs"`, `"a_star"`, `"sabre"`
  - a custom pairwise callable: `(start, end) -> list[int]` — same interface as v1.0.x
  - `None`: treated as `"bfs"` (matches v1.0.x default behavior)
- Two-tier strategy contract: pairwise algorithms (BFS, A\*) share `pairwise_route`; SABRE implements the whole-circuit contract directly

### SABRE Layout Algorithm
Initial mapping discovery using forward-backward trial routing
(Li, Ding, Xie 2019). Uses SABRE routing internally as the trial router.
- Available via `LayoutPass(coupling_map, "sabre")` or `transpile(..., layout_algorithm="sabre")`

### A\* Routing Algorithm
A\* shortest-path search over the coupling map's directed graph, using
`coupling_map.distance(node, end)` as the admissible heuristic.
- Architecture-ready for noise-aware weighted edges; matches BFS performance
  on today's unweighted graphs
- Available via `BasicSwapRouter(coupling_map, "a_star")` or `transpile(..., pathfinder="a_star")`

### SABRE Routing Algorithm
Whole-circuit heuristic swap selection with front-layer lookahead
(Li, Ding, Xie 2019). Maintains a front layer of executable gates and
picks each swap by scoring candidates against a heuristic that considers
both immediate gates and the next `EXTENDED_SET_SIZE=20` gates (weighted
`LOOKAHEAD_WEIGHT=0.5`).
- Per-qubit decay term from the original paper omitted in this release; can be
  added later if benchmarks warrant it
- Available via `BasicSwapRouter(coupling_map, "sabre")` or `transpile(..., pathfinder="sabre")`

## Bug Fixes

### Sparse-Layout Routing (KeyError on unmapped physical qubits)
When a circuit had fewer logical qubits than the coupling map's physical
qubits (i.e. essentially any real circuit on FakeNairobiV2 / FakeBrisbane /
etc.), routing could crash with `KeyError` on the inverse-position dict
lookup if the chosen path ran through an unmapped physical qubit.

Fixed in three places with general swap-update logic that handles `None`
on either side of the swap:
- `tessera/routing/pairwise.py:pairwise_route` (engine used by BFS / A\*)
- `tessera/routing/sabre.py:sabre_route` (main loop swap application)
- `tessera/layouts/sabre.py:_trial_route_final_mapping` (replay-swaps helper)

### SABRE Deadlock on Sparse Layouts
A defensive filter restricting SABRE candidate swaps to currently-mapped
physical qubits (added to avoid the above KeyError) could cause an infinite
loop when the only path between two front-layer qubits ran through unmapped
qubits. With no candidate able to reduce the heuristic, SABRE picked, applied,
re-checked, and looped forever.

Fixed by removing the filter and giving the swap-update logic proper
sparse-layout handling instead. SABRE can now route through unmapped
"spare" qubits when needed.

### `to_qiskit` Output Register Sizing
The output `QuantumCircuit` was sized from `max(layout.values()) + 1`,
which undersized the register when routing had pushed qubits onto physical
indices higher than anything in the (sparse) layout. Resulting in
`CircuitError: Index N out of range for size M`.

Fixed by sizing the output register to cover both the layout's max physical
qubit and the max qubit referenced in the routed instructions:
- `tessera/converters.py:to_qiskit`

### `BasicSwapRouter` Rejected `None` Path Finder
`TesseraTranspiler` defaults `pathfinder=None` and forwards it through to
`BasicSwapRouter`. The new resolution logic raised on `None`, breaking
existing transpiler usage.

Fixed by treating `None` as `"bfs"` at the top of `BasicSwapRouter.__init__`
for backwards compatibility.

## Deprecations

### `DenseLayoutPass` (deprecation shim)
`tessera/passes/dense_layout_pass.py` is now a thin backwards-compatibility
shim that delegates to `LayoutPass(coupling_map, "dense")` and emits a
`DeprecationWarning` on construction. Existing code keeps working;
new code should use `LayoutPass` directly.

May be removed in a future release.

---

## Removals

### `TrivialPass`
Removed in favor of `LayoutPass(coupling_map, "trivial")`. The algorithm
itself is preserved in `tessera/layouts/trivial.py` and registered under
the `"trivial"` key in `LAYOUT_REGISTRY`.

This is a breaking change for any user that imported `TrivialPass`
directly. Migration: replace
```python
from tessera.passes.trivial_pass import TrivialPass
TrivialPass(coupling_map).run(circuit)
```
with
```python
from tessera.passes.layout_pass import LayoutPass
LayoutPass(coupling_map, "trivial").run(circuit)
```

## Migration Guide

Existing code keeps working at default settings. Two opt-in surface changes:

1. **`TrivialPass` callers** must switch to `LayoutPass(cm, "trivial")`
   (see Removals above).

2. **`DenseLayoutPass` callers** keep working but will see a
   `DeprecationWarning`. Switch to `LayoutPass(cm, "dense")` to silence
   the warning and align with the new architecture.

Everything else is additive:
- `layout_algorithm` (new) selects layout algorithm; default `"dense"` matches v1.0.x.
- `pathfinder` (existing name, expanded behavior) selects routing algorithm; default `"bfs"` matches v1.0.x. The parameter kept its v1.0.x name for back-compat — it's the routing-side counterpart to the new `layout_algorithm`, just with an older name.
- `optimization_iterations` (new); default `1` matches v1.0.x.
- `max_iterations` (new); only used when `optimization_iterations=-1`.

## Internal / Refactor

- New shared engine `tessera/routing/pairwise.py:pairwise_route` extracted
  from the old `BasicSwapRouter.run` body. Hosts BFS and A\* via thin strategy
  wrappers in `ROUTING_REGISTRY`. SABRE bypasses this engine because its
  whole-circuit swap selection doesn't fit the pairwise contract.
- Two-tier routing strategy contract documented in `routing_registry.py`
  and `pairwise.py` module docstrings.
- `BasicSwapRouter` reduced to a thin shell that resolves algorithm choice
  in `__init__` and calls `self.strategy_fn(circuit, coupling_map)` in `run`.
- `LayoutPass` follows the same shape: resolve in `__init__`, trivial `run`.
- Algorithm registries store callables directly (not metadata dicts), unlike
  the hardware-name registries (`BACKEND_REGISTRY`, `COUPLING_MAP_REGISTRY`)
  which store dicts of associated metadata. Convention documented in the
  registry module docstrings.
